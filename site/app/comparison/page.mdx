# Is Kora a fit?

Kora is not a better Python or TypeScript. It is a pre-alpha language that
bundles a static checker, model outcomes, data-flow policy, budgets, replay,
and durable effects for one narrow job: sensitive document workflows.

If those concerns are not tightly coupled in your product, adopting a new
language is not justified.

## The practical comparison

| Need | Established stack | Kora today |
| --- | --- | --- |
| Call models and tools | Mature SDKs and many integrations | A smaller built-in surface |
| Structured output | Schema libraries such as Pydantic, Zod, or BAML | Kora `type` declarations validated at the model boundary |
| Workflow orchestration | LangGraph, Temporal, cloud workflow services, or queues | Language control flow plus opt-in durable journals |
| Sensitive-data policy | Application code, policy middleware, DLP, and review | `classified`, scoped `declassify`, named sinks, and runtime enforcement |
| Model test fixtures | Framework mocks or custom recordings | Native `--record` and `--replay` cassettes |
| Ecosystem and hiring | Strong | Very early |
| Compatibility history | Years of production use | No stable compatibility promise |
| Security evidence | Depends on the chosen stack | No independent audit yet |

The Kora advantage is composition. The same program can say what data may
leave, what shape may return, what the work may spend, and what must replay.
The disadvantage is equally clear: your team must adopt a young language and
its small ecosystem.

## Choose Kora only when

- The workflow processes sensitive claims, invoices, compliance records, or
  internal operational documents.
- A named data boundary matters more than broad library access.
- Deterministic replay and explicit model failure outcomes are required.
- The workflow can stay small and push specialist computation to a package,
  helper, MCP server, or Python sidecar.
- You can tolerate pre-alpha APIs and participate in shaping the language.

## Do not choose Kora when

- You need a general application language or a large package ecosystem.
- A normal SDK call and schema validation already solve the problem.
- Your team needs a proven production platform today.
- You need high-throughput numeric work inside the language.
- You cannot accept a new toolchain and an immature hiring market.

## What Kora actually checks

```kora
type Claim:
    id: str
    classified notes: str

type Decision:
    route: str
    reason: str

def decide(claim: Claim) -> str:
    declassify claim.notes as approved_notes for local_model:
        result: Decision = analyze(
            {"id": claim.id, "notes": approved_notes},
            "route this claim for review"
        )

    match result:
        case Ok(decision):
            return decision.route
        case Uncertain(reason):
            return f"human: {reason}"
        case Exhausted(meter):
            return f"budget: {meter}"
        case Failed(why):
            return f"provider: {why}"
```

Before effects start, Kora checks local declared types, function and
constructor arity, field access, control-flow placement, and direct classified
flow into `analyze`. At runtime it validates model output, enforces the named
sink policy, meters budgets, and records effects when durability is enabled.
Dynamic integrations remain runtime boundaries.

## The market position

Kora should be evaluated as a policy-aware workflow language, not an agent
framework and not a Python replacement. The proof it still needs is concrete:
three design partners, one published end-to-end document workflow, a public
comparison against an established stack, and an independent security review.

Until that evidence exists, the honest reason to try Kora is exploration, not
production readiness.
