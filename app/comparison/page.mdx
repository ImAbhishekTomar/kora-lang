# Comparison

The quickest way to understand Kora is to put the same workflow side by side.

Here, every version reads a support ticket, asks a model to classify it, and prints the result.

## Python

```python
from pydantic import BaseModel
from openai import OpenAI

class Ticket(BaseModel):
    severity: str
    summary: str

client = OpenAI()

def triage(raw: str) -> Ticket:
    response = client.beta.chat.completions.parse(
        model="gpt-4o",
        messages=[
            {"role": "user", "content": f"Classify this ticket: {raw}"}
        ],
        response_format=Ticket,
    )
    return response.choices[0].message.parsed

ticket = triage("Checkout fails for every customer")
print(f"{ticket.severity}: {ticket.summary}")
```

Python is a great general-purpose choice with a rich AI ecosystem. In this example, the reliability pieces come from libraries and your own conventions: the schema, client setup, retries, logging, replay, and failure handling.

## TypeScript

```typescript
import OpenAI from "openai";
import { z } from "zod";
import { zodTextFormat } from "openai/helpers/zod";

const Ticket = z.object({
  severity: z.string(),
  summary: z.string(),
});

const client = new OpenAI();

async function triage(raw: string) {
  const response = await client.responses.parse({
    model: "gpt-4o",
    input: `Classify this ticket: ${raw}`,
    text: { format: zodTextFormat(Ticket, "ticket") },
  });
  return response.output_parsed;
}

const ticket = await triage("Checkout fails for every customer");
console.log(`${ticket.severity}: ${ticket.summary}`);
```

TypeScript gives you excellent tooling and static types. It is especially comfortable for web teams. The async boundary is explicit, but workflow concerns such as model uncertainty, token budgets, durable pauses, and record/replay still need to be designed around the call.

## Kora

```kora
type Ticket:
    severity: str
    summary: str

def main():
    result: Ticket = analyze(
        "Checkout fails for every customer",
        "classify this support ticket"
    )

    match result:
        case Ok(ticket):
            print(f"{ticket.severity}: {ticket.summary}")
        case Uncertain(reason):
            print(f"Could not classify: {reason}")
```

Kora makes the workflow boundary part of the language. The declared type describes the model output, `Uncertain` is a normal result, and the runtime can record the call for deterministic replay.

## Where Kora helps

Kora is not trying to replace Python or TypeScript for every kind of software. Its focus is the part where ordinary code meets models, tools, data, and human decisions.

| Concern | Python / TypeScript | Kora |
| --- | --- | --- |
| Model output | Schema libraries and conventions | Declared result type with `Ok` / `Uncertain` |
| Testing model calls | Mocking and custom fixtures | Native record/replay cassettes |
| Token limits | Application-level tracking | Native budget constructs |
| Agent workflows | Frameworks plus async/job infrastructure | Language constructs for agents and parallel work |
| Sensitive data | Libraries and careful review | Scoped `declassify` checks |
| Human approval | Queue or workflow service | Durable `ask_human` suspension |
| Parallelism | Threads limited by the GIL, or multiprocessing | `parallel for` on OS threads, isolated heaps |
| Concurrency style | `async`/`await` spreading through callers | Blocking calls, no function colouring |
| Packaging | pip, Poetry, uv, Conda, native wheels | One binary, one `kora.toml` |

The promise is simple: fewer important reliability decisions hidden in glue code.

## The Python constraints Kora removes

Most of these are not about syntax. They are constraints that show up once an
AI workflow grows past one script.

### The GIL

CPython's global interpreter lock stops normal threads from running Python
bytecode in parallel. An agent system that parses, embeds, ranks, and calls
models at the same time usually escapes into multiprocessing, native
extensions, or separate worker services.

Kora has no interpreter lock. `parallel for` fans out across OS threads with a
work-stealing scheduler, and it is safe because agents share nothing: each one
gets its own heap, and values are copied across the boundary rather than
aliased.

```kora
def main():
    with budget(max_tokens = 50000):
        results = parallel for t in tickets:
            triage(t)
```

That is the whole setup. No pool, no queue, no `if __name__ == "__main__"`
guard, no pickling rules.

### Async that spreads

LLM code waits: on APIs, tools, databases, and model responses. In Python one
`async def` tends to turn its callers async too, and the mix of sync
libraries, async libraries, streaming, and retries is where subtle event-loop
bugs live.

Kora has no `async` and no `await`. A model call, a tool call, and an HTTP
request all block the thread they run on, and concurrency comes from threads
instead of an event loop. There is no second colour of function to keep in
sync with the first.

The cost we accept: a blocked call holds a thread. That suits agent-scale
concurrency, not a hundred thousand open sockets.

### Types that are only hints

Python type hints are optional and, by default, mean nothing at runtime.
Pydantic helps, but it is a layer you remember to apply, at the boundaries you
remember to guard.

In Kora types are checked before the program runs, and the model boundary is
part of that check. `analyze` is given your declared type, constrains the
model's output to it, validates the reply, and returns `Ok(T)`,
`Uncertain(reason)`, or `Exhausted(meter)`. A model that answers off-schema
produces `Uncertain`, which is a value you match on, not an exception thrown
somewhere deep in a request handler.

### Packaging

pip, Poetry, uv, Conda, virtualenvs, native wheels, and Python version drift
between a laptop and a container.

Kora is a single binary and one `kora.toml`. There is no environment to
recreate, so a program that runs locally runs the same way in a container.
Python is available as an escape hatch, and it stays optional: a program
without `use python` needs no Python installed at all. When you do use it,
Python runs in a sidecar process with JSON crossing the boundary, which is
also why embedding CPython, and its GIL, never happens inside Kora.

### Performance, honestly

Kora's runtime is Rust, so there is no per-object interpreter overhead of the
CPython kind, and an agent's heap is freed whole when it exits. Both matter
when you hold large contexts or run many sessions at once.

But the evaluator is a tree-walking interpreter today, and raw compute
throughput is not yet a reason to choose Kora. Heavy numeric loops, embedding
math, and document crunching still belong behind a tool call, a native
library, or the Python sidecar. What Kora removes is the need to escape the
language to get *parallelism*. It does not claim to be fast at everything.

Rather than leave that as a claim, the repository carries a benchmark set and
a committed baseline. On a ten-core laptop, running the whole program including
start-up:

| what it measures | best of 7 |
| --- | ---: |
| start-up, parse, and name resolution | 4.3 ms |
| 400,000 arithmetic loop iterations | 220 ms |
| a 4000-element JSON document, parsed 100 times | 234 ms |
| 20,000 CSV rows, parsed 10 times | 172 ms |
| eight units of CPU work, one thread | 426 ms |
| the same eight units through `parallel for` | 118 ms |

That last pair is the point: 3.6x on ten cores, with no locks to write and no
worker processes to manage. And the gap between the arithmetic row and the CSV
row is the honest picture of where Kora is fast today. Work that reaches Rust
is quick; work that stays in the tree walker is not, and that is exactly the
gap a bytecode VM closes.

You can reproduce all of it, and a pull request is measured against its own
base commit on one machine, so a change that taxes the interpreter shows up
before it ships:

```bash
cargo build --release -p kora-cli
python3 scripts/bench.py
python3 scripts/bench.py --against main
```

## The honest trade-off

Python and TypeScript have bigger ecosystems, more libraries, and more production history. Kora is earlier and has fewer integrations.

Kora becomes useful when your main problem is not “how do I call a model?” but “how do I make this AI workflow typed, testable, affordable, observable, and safe as it grows?”
